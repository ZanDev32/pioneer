<objective>
Collapse the three async executor bypasses onto the shared seam, add the POSIX-only platform guard, then write the integration layer that drives all 12 tool handlers with a single mock boundary and turns on the coverage floors.

Purpose: research finding B-4 shows `params.async` branches in build/upload/test call the child-process module inline, so a `vi.mock` of the executor never sees them — tests would hit the real CLI and silently pass. Fixing the seam first makes every integration test honest; the guard converts a raw Windows spawn failure into a named error (D-22).
Output: one executor path, eight integration test files, and enforced coverage thresholds.

Ordering note: this plan depends on 03-02 because the handler tests stub the server with `registerTool`, and on 03-03 because the coverage floor assumes the unit layer already exists.

Scope note (15 files, accepted with measurement): the 15 paths are one concern in three stages that cannot be reordered — task 1 changes 4 tool modules plus `src/errors.js` and adds the guard test (6 paths), tasks 2-3 add 8 integration files that only become honest after that seam exists, and `vitest.config.js` carries the thresholds that need those tests. `estimate-check --tokens 96000 --calibrated` reports ratio 0.96 against the 100k budget with `over_budget: false`, confidence low, and `calibration_applied: false` (factor 1, no completed samples) — so the number is an uncalibrated projection rather than a measured cost. What is measured today: the five pre-existing modules total 1,604 lines / 54,827 chars (`build.js` 297, `upload.js` 236, `test.js` 347, `monitor.js` 552, `errors.js` 172), i.e. ≈15k tokens for one pass, while the eight test paths are new files (authored, never read back) and `vitest.config.js` is a small delta on the file 03-01 creates. Roughly 85k of the zone therefore remains for authoring and test output — the headroom the low-confidence projection does not price in. The one alternative — relocating a seam-adjacent edit into 03-03 (wave 2) — was rejected because the only movable unit is the POSIX monitor guard, which is not on the async-executor seam (that seam is `build.js`/`upload.js`/`test.js`), and moving it would shift D-22/NFR-2 ownership into a pure-function unit plan while leaving every coupled path here. No wave-consistent split exists without adding a ninth plan and a new `depends_on` edge into 03-06 — both ruled out for this revision; a seam-then-tests split inside the same plan would still hand one executor the same 15 files. If the estimate does run hot, the executor reports it after task 2 — the coverage thresholds in task 3 are locked by D-23/D-24 and are never the thing to trim.
</objective>
